# GitHub 学习路线与重点学习内容

> 目标：6 周从零到能独立完成多人协作、并给开源项目提交合格 PR。
> 学习比例建议：**20% 看资料，80% 动手**。每个命令都在自己的仓库里试一遍，练废了就删仓库重建，成本为零。

---

## 0. 先分清 Git 和 GitHub

| | Git | GitHub |
|---|---|---|
| 是什么 | 本地版本控制系统（一个软件） | 基于 Git 的代码托管 + 协作平台（一个网站/服务） |
| 管什么 | 提交历史、分支、合并 | 仓库托管、PR、Issue、Review、CI、项目管理 |
| 离线能用吗 | 能 | 不能 |

**结论**：Git 是地基，GitHub 是建筑。先学 Git 的本地操作，再学 GitHub 的协作机制。跳过 Git 直接学 GitHub，后面 90% 的困惑（冲突、rebase、强推）都无解。

---

## 1. 六周学习地图

```
第 0 天    环境准备（账号 + Git + SSH）
第 1 周    Git 核心：提交、历史、撤销、分支、合并
第 2 周    GitHub 基础：仓库、README、远程同步、Issue
第 3 周    协作核心：分支规范、Pull Request、Code Review、冲突解决
第 4 周    工程化：GitHub Actions、Pages、Releases、Projects
第 5 周    开源实战：Fork 流程、社区礼仪、第一个 PR
第 6 周    进阶：安全（2FA / 密钥 / Dependabot）、CLI、团队权限、提交规范
```

每周约 5～7 小时。每周结构：**1 小时看概念 → 3 小时动手 → 1 小时复盘写笔记**。笔记本身就用 Git 管理，一箭双雕。

## 2. 阶段 0：环境准备（半天）

- [ ] 注册 GitHub 账号，**立刻开启 2FA**（2024 起强制，早开早省事）
- [ ] 安装 Git，配置身份（提交记录靠这个）
  ```bash
  git config --global user.name "你的名字"
  git config --global user.email "你的邮箱"
  git config --global init.defaultBranch main
  ```
- [ ] 生成 SSH key 并测试（比每次输密码舒服得多）
  ```bash
  ssh-keygen -t ed25519 -C "你的邮箱"
  cat ~/.ssh/id_ed25519.pub       # 复制内容粘贴到 GitHub → Settings → SSH keys
  ssh -T git@github.com          # 看到 "successfully authenticated" 即成功
  ```
- [ ] 装 GitHub CLI（可选但强烈推荐）：`gh auth login`

> 前两周**强制用命令行**，图形界面会让你不知道自己在做什么。熟练后再用 VS Code 的 Git 面板或 GitHub Desktop。

## 3. 阶段 1：Git 核心（第 1 周）★最重要

### 3.1 必须先建立的模型：四个区域

```
工作区            暂存区            本地仓库           远程仓库
(改文件)  --add-->  (index) --commit--> (HEAD) --push--> (origin)
   ↑                                            ↑
   └──────────── restore ───────────────────────┘
```

- `git add` = 挑选这次要提交的改动
- `git commit` = 在本地拍一张快照
- `git push` = 把快照同步到服务器
- 90% 的 Git 报错，都是"你以为改动在 X 区，其实在 Y 区"

### 3.2 第一周必须练熟的命令

| 场景 | 命令 |
|---|---|
| 初始化仓库 | `git init` |
| 克隆远程仓库 | `git clone <url>` |
| 看状态（最常用） | `git status` |
| 暂存单个 / 逐块暂存 | `git add <file>` / `git add -p` |
| 提交 | `git commit -m "feat: 新增登录"` |
| 看历史（图形化） | `git log --oneline --graph --all` |
| 看差异 | `git diff` / `git diff --staged` |
| 新建并切换分支 | `git switch -c feat/login` |
| 切换分支 | `git switch main` |
| 合并分支 | `git merge feat/login` |
| 变基 | `git rebase main` |
| 暂存手头改动 | `git stash push -m "wip"` / `git stash pop` |
| 丢掉工作区改动 | `git restore <file>` |
| 取消暂存 | `git restore --staged <file>` |
| 修改最近一次提交 | `git commit --amend` |
| 回退本地提交（保留改动） | `git reset --soft HEAD~1` |
| 撤销**已推送**的提交 | `git revert <sha>` |
| 挑一个提交到当前分支 | `git cherry-pick <sha>` |
| 找回"丢失"的提交/分支 | `git reflog` |

### 3.3 必须搞清楚的四组辨析

**① reset 的三种模式**（危险程度递增）

| 模式 | HEAD | 暂存区 | 工作区 | 用途 |
|---|---|---|---|---|
| `--soft` | 回退 | 保留 | 保留 | 想重新组织提交 |
| `--mixed`（默认） | 回退 | 清空 | 保留 | 取消提交+取消暂存 |
| `--hard` | 回退 | 清空 | **丢弃** | ⚠️ 真正的删代码 |

**② merge vs rebase**
- `merge`：保留分叉历史，安全，**共享分支用它**
- `rebase`：把提交搬到目标分支顶端，历史成一条直线，**只用于自己尚未推送的本地分支**
- 铁律：**不要 rebase 别人已经拉取过的分支**，否则会制造一堆重复提交

**③ fetch vs pull**
- `git fetch`：只下载，不动你的工作区
- `git pull`：= fetch + merge（或 `pull --rebase` = fetch + rebase）
- 想先看清远端改了什么再决定：先 `fetch`，再 `git log HEAD..origin/main`

**④ fork vs clone**
- `fork`：在**服务器上**复制一份仓库到你名下
- `clone`：把仓库下载到**本地**
- 开源贡献常用组合：`fork` 原仓库 → `clone` 自己的 fork → 加 `upstream` 指回原仓库

### 3.4 冲突是怎么产生的、怎么解

冲突 = 两个人改了**同一处**，Git 不敢替你决定。

```bash
git status                   # 1. 找出冲突文件（both modified）
# 2. 打开文件，找到标记
#    <<<<<<< HEAD
#    你的版本
#    =======
#    对方版本
#    >>>>>>> feat/login
# 3. 手动改成你想要的最终结果，删掉三行标记
git add <file>               # 4. 标记为已解决
git commit                   # 5a. merge 场景：正常提交
git rebase --continue        # 5b. rebase 场景
# 想反悔：
git merge --abort            # 或
git rebase --abort
```

### 3.5 第一周必做练习（做完这些才算过关）

- [ ] 建一个本地仓库，做 10 次提交，用 `git log --graph` 看懂历史
- [ ] 建 `feat/a`、`feat/b` 两个分支改同一行，**故意制造 3 次冲突**并解决
- [ ] 用 `git reset --soft/--mixed/--hard` 各试一次，观察文件变化
- [ ] 用 `git revert` 撤销一个提交，理解它为什么"多出一条新提交"
- [ ] 误删分支后，用 `git reflog` 找回它（这招能救命）
- [ ] 用 `git stash` 保存半成品，切分支干活，再切回来恢复
- [ ] 把 `node_modules/`、`dist/`、`.env` 写进 `.gitignore` 并验证生效

## 4. 阶段 2：GitHub 平台基础（第 2 周）

### 4.1 仓库页面要看得懂

| 区域 | 作用 |
|---|---|
| Code | 文件树、分支切换、提交历史 |
| Issues | 任务 / Bug / 讨论，带 label、assignee、milestone |
| Pull requests | 代码变更评审与合并 |
| Actions | CI/CD 流水线 |
| Projects | 看板式项目管理 |
| Wiki | 项目文档 |
| Insights | 提交频率、贡献者、流量 |

### 4.2 README 是仓库的门面

必须包含：一句话说明这是什么 → 截图/演示 → 安装 → 使用示例 → 目录结构 → 如何贡献 → License。
善用 `badge`（构建状态、版本、License）和 Markdown 表格。

### 4.3 远程仓库操作

```bash
git remote add origin git@github.com:user/repo.git
git remote -v                        # 查看远程地址
git push -u origin main              # 首次推送并建立追踪关系
git push                             # 之后直接推
git fetch --all --prune              # 拉取所有远端并清理已删除分支
git pull --rebase                    # 推荐：拉取并线性整合
```

### 4.4 Issue 的正确用法

- 一个 Issue 只做一件事，标题写清"现象 + 影响"
- 用 `Closes #12` / `Fixes #12` 写在 PR 描述里，合并时自动关闭 Issue
- 学会用 label（`bug` / `enhancement` / `good first issue`）和 milestone
- 用 Issue 模板（`.github/ISSUE_TEMPLATE/`）规范化提问

### 4.5 顺手做的两件小事

- [ ] 建 `你的用户名/你的用户名` 仓库，写 **Profile README**（个人主页门面）
- [ ] 学会 Markdown：标题、列表、表格、代码块、任务列表、折叠块、Mermaid 图

## 5. 阶段 3：协作核心 —— PR 工作流（第 3 周）★最重要

### 5.1 标准八步（背下来）

```bash
# 1. 同步主干
git switch main && git pull --rebase

# 2. 从最新主干开分支（永远不要直接在 main 上改）
git switch -c feat/user-profile

# 3. 小步提交（一个提交只做一件事）
git add -p
git commit -m "feat: 增加用户资料卡片"

# 4. 推到远端
git push -u origin feat/user-profile

# 5. 在 GitHub 上开 PR（或 gh pr create）
# 6. CI 通过 + 按 review 意见继续在同一分支提交、push
# 7. Squash and merge 合并到 main
# 8. 清理
git switch main && git pull --prune
git branch -d feat/user-profile
```

### 5.2 一份合格的 PR 描述

```markdown
## 做了什么
新增用户资料卡片组件。

## 为什么
Closes #42，用户反馈个人页缺少关键信息。

## 怎么验证
1. 登录后进入 /profile
2. 确认卡片显示头像、昵称、加入时间
3. 断网时应显示占位骨架

## 备注
- 已补单测，覆盖率 82% → 87%
- 不涉及数据库变更
```

要点：**小而聚焦**。一个 PR 超过 400 行改动，评审质量会断崖式下降。

### 5.3 Code Review 礼仪

作为作者：主动说明思路和取舍，别等别人猜；对意见逐条回复（改了就说明，不改就讲理由）。
作为评审者：先看整体设计再看细节；用"建议"而非"命令"的语气；区分「必须改」和「可以更好」。

### 5.4 分支保护（Branch protection）

在 Settings → Branches 给 `main` 配置：
- 禁止直接 push，必须走 PR
- 至少 1 人 approve
- CI 必须通过才能合并
- 合并后自动删除分支
- （可选）要求线性历史 / 要求签名提交

**这是团队协作和"随便玩玩"的分水岭。**

### 5.5 第三周练习

- [ ] 用两个账号（或拉一个朋友）完整跑一遍：fork → 分支 → PR → review 提意见 → 修改 → 合并
- [ ] 在 PR 里故意制造冲突，用本地 rebase 解决后再推送
- [ ] 给自己仓库的 `main` 开启分支保护，体验被拒绝 push
- [ ] 练习 `git commit --amend` 修正提交信息后 `push --force-with-lease`（**只用在自己分支**）

## 6. 阶段 4：让仓库"活"起来（第 4 周）

### 6.1 GitHub Actions（最小可用）

`.github/workflows/ci.yml`：

```yaml
name: CI
on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npm test
```

要理解的四个概念：**on**（什么时候触发）、**jobs**（干什么活）、**steps**（一步步怎么做）、**uses vs run**（用现成 action vs 跑命令）。
进阶：`secrets`（存密钥，`${{ secrets.TOKEN }}`）、`matrix`（多版本并行）、`cache`（加速）、`needs`（任务依赖）。

### 6.2 GitHub Pages

Settings → Pages 选分支即可，或写一个 Actions 部署静态站。用来放简历、博客、项目文档，零成本。

### 6.3 Releases 与 Tag

```bash
git tag -a v1.0.0 -m "首个稳定版"
git push origin v1.0.0
```
配合 Release 写变更说明（Changelog），这是"交付"和"提交代码"的区别。

### 6.4 其他值得配的东西

- `.github/PULL_REQUEST_TEMPLATE.md` —— 统一 PR 描述
- `.github/CODEOWNERS` —— 指定某目录必须谁来 review
- `Projects` —— 看板管理任务流（Todo / In progress / Done）
- `Dependabot` —— 自动提依赖升级 PR
- `Discussions` —— 非 bug 的开放式讨论

## 7. 阶段 5：开源贡献实战（第 5 周）

### 7.1 找项目的正确姿势

1. 从**你正在用的库**入手（有真实痛点，动机最强）
2. 搜索 `label:"good first issue"` + 你熟悉的语言
3. 看仓库是否活跃：最近提交、Issue 回复速度、是否有 CONTRIBUTING.md
4. 避开：长期无人维护、PR 堆积几百个没人理的仓库

### 7.2 Fork 工作流（开源标准流程）

```bash
# 1. 网页上 fork 原仓库到自己账号
git clone git@github.com:你/repo.git
cd repo

# 2. 加原仓库为 upstream
git remote add upstream git@github.com:原作者/repo.git

# 3. 每次开工前同步
git fetch upstream
git switch main
git reset --hard upstream/main     # 让自己的 main 与原仓库一致

# 4. 开分支、改、提交、push 到自己的 fork
git switch -c fix/typo-readme
git commit -am "docs: 修正 README 拼写"
git push -u origin fix/typo-readme

# 5. 在 GitHub 上向原仓库开 PR
```

### 7.3 社区礼仪（决定你的 PR 会不会被无视）

- **先开 Issue 讨论，再提 PR**（大改动尤其如此），别突然甩一个 2000 行的 PR
- 一个 PR 只解决一个问题
- 遵守项目的代码风格、提交信息规范、CLA/DCO 要求
- 被要求修改时，**在同一分支继续提交**，不要关掉重开
- 耐心：维护者都是业余时间在做，一两周没回复很正常
- 第一次贡献从**文档、拼写、翻译、测试**入手，成功率高

### 7.4 第五周练习

- [ ] 在 [first-contributions](https://github.com/firstcontributions/first-contributions) 完成第一次 PR
- [ ] 给自己常用的某个库提一个文档改进 PR
- [ ] 找一个 `good first issue`，先留言认领，再动手

## 8. 阶段 6：进阶与安全（第 6 周）

### 8.1 安全（血的教训都在这）

- **永远不要提交密钥**。`.env`、`*.pem`、`id_rsa` 全部进 `.gitignore`
- 已经提交了怎么办：**立刻在服务商后台吊销/轮换密钥**（历史里删掉也不算安全，别人可能已经拉走了）
- 开 Dependabot alerts + Secret scanning
- 用 GPG 签名提交（`git commit -S`），证明提交确实来自你

### 8.2 提交信息规范（Conventional Commits）

```
<type>(<scope>): <subject>

feat: 新增用户登录
fix: 修复分页越界
docs: 更新 API 说明
refactor: 抽离请求封装
test: 补充边界用例
chore: 升级依赖
```

好处：历史可读、能自动生成 Changelog、能按语义化版本发版。

### 8.3 团队与权限

- Organization → Team → 仓库权限（Read / Triage / Write / Maintain / Admin）
- 最小权限原则：默认给 Read，按需升级
- 用 Rulesets / Branch protection 而不是靠人自觉

### 8.4 GitHub CLI 常用

```bash
gh auth login
gh repo create myproj --public --clone
gh pr create --fill
gh pr list / gh pr checkout 123
gh issue list --label bug
gh run list / gh run watch
```

### 8.5 知道但不必精通

Git LFS（大文件）、submodule（嵌套仓库）、Git Flow vs Trunk-based 开发、Monorepo、Codespaces。

## 10. 五个递进练习项目

1. **本地练功房**：一个空仓库，专门用来制造冲突、试 reset、用 reflog 救场。练坏了就删。
2. **个人知识库仓库**：把你的学习笔记用 Git 管理，全程命令行，配好 README + `.gitignore` + 规范提交信息。
3. **双人协作演练**：两个账号 fork/PR 互相 review，刻意制造一次冲突并解决。
4. **工程化改造**：给项目 2 或 3 加 GitHub Actions 自动测试 + Pages 部署 + PR 模板 + 分支保护。
5. **真实开源 PR**：从文档/翻译/测试入手，走完 fork → PR → review → merge 全流程。

## 11. 常见坑（提前知道能省很多时间）

- ❌ 直接在 `main` 上开发并 push —— 团队里这是事故
- ❌ 提交 `node_modules/`、`dist/`、`.env`、密钥
- ❌ 对共享分支 `git push --force` —— 会覆盖别人提交；非用不可时用 `--force-with-lease`
- ❌ rebase 已经推送并被别人拉取的分支
- ❌ 一次提交混杂格式化 + 功能 + 重构，导致 review 无法进行
- ❌ commit message 写 "update"、"fix"、"aaa"
- ❌ 把 >100MB 的文件直接提交（会被 GitHub 拒绝，需 LFS）
- ❌ 删了分支才发现没合并 —— 用 `git reflog` 还能救
- ❌ 在网页上直接改代码，导致本地与远端分叉
- ❌ 不看 CI 报错就 @ 人问"为什么合不了"

## 14. 一句话总结

**GitHub 不难，难的是"敢操作"和"守规范"。** 先把撤销链路（restore / reset / revert / reflog）练到条件反射，你就再也不怕弄坏仓库；再把 PR 流程和小步提交变成肌肉记忆，你就具备了在任何团队协作的能力。
